## Background

`planny serve --detach` sends the detached server's output to
`<tmpdir>/planny-serve-<port>.log`, named by the requested port
(detachLogPath, src/server.ts:137). Every detach opens the file in
append mode (src/server.ts:155). `planny serve --stop` kills the
server and clears a stale `.planny/serve.json`, but no planny command
prints, lists, or deletes log files. The success output never shows
the path (src/cli.ts:894-907); only a failed detach prints it. The OS
temp-dir policy is the only cleanup.

The operator asked (a) whether `--stop` should remove the log and (b)
for a way to identify and clean up old logs. A count on this machine
supports (b): /tmp held 43 planny-serve-*.log files on 2026-09-01.
Most are 70-byte leftovers from the test suite, which detaches onto
random ports in the real temp dir — that leak has its own fix task,
t217. Also, `planny-serve-0.log` grows without bound because a
`--port 0` request names the log by the requested port, not the bound
one. What remains here is the design for real use.

## Why this comes to you (the operator)

The flags and files are an operational surface you use, and the
trade-off between a tidy temp dir and post-mortem evidence is a
product choice.

## Proposal (a) — bound each log: truncate on start

Open the log with mode 'w' instead of 'a' (src/server.ts:155), so a
log holds exactly one run.

*Pros:* bounds growth with no new flag. Also fixes a misattribution:
when a detach fails before the child writes, the error prints the tail
of the appended log (src/server.ts:179), which can be a previous run's
output shown as this failure's evidence.
*Cons:* a restart erases the previous run's log.

## Proposal (b) — identify: print the log path

Show the path in the success output: `serve --detach` prints it beside
the URL and pid (src/cli.ts:907), and `serve --stop` prints "log kept
at <path>" (src/cli.ts:894).

*Pros:* answers "where is the post-mortem" at the exact moments the
question comes up; no new command.
*Cons:* slightly longer output lines.

## Proposal (c) — clean up: sweep stale logs during detach

After a successful detach, delete planny-serve-*.log files older than
seven days whose port no longer answers as a planny server. Automatic,
no new surface. With (a) and t217 done, the sweep rarely finds
anything.

*Pros:* self-cleaning, nothing for the operator to remember.
*Cons:* deletes quietly; on a rarely used machine an old crash log can
vanish before anyone reads it.

## Alternative options

- `planny serve --stop --clean-log` (the original question). Ruled out
  for now: it destroys the post-mortem at the moment it is most
  wanted, and it does not touch the other stale files.
- A listing and cleaning command (`planny serve --logs` /
  `--clean-logs`): show each file with size, age, and live or dead;
  delete the dead ones on request. More explicit than (c), more
  surface. Re-open this if silent deletion feels wrong.
- Key the log by store directory name instead of port: the file name
  then says which board it belongs to, and `--port 0` stops writing to
  a file named "0". Costs the predictable per-port path. Fold into (b)
  if wanted.
- Do nothing: the OS clears the temp dir on its own schedule.

## Needed from you

Letters to build. Recommended: "a+b"; add "c" if the stale files
annoy you. "leave it" is also an answer.

## When

No deadline; nothing blocks on this. Waiting costs stale temp files
and an occasionally misleading failure message.
