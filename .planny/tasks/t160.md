## Background

In a project that uses planny (the claudebox coverage project), a session tracked review debt in a markdown file with per-item status ticks and a "tick items off here" instruction — a parallel queue the planny store should have owned. The skill's rules trigger on the words "task", "plan", "feature request", "bug report"; work disguised as a "queue", "register", "backlog", "follow-ups" or "review debt" section of a report does not pattern-match those words, so a session writes checkboxes into markdown instead of running planny add. The observable tell is per-item status: checkboxes, tick marks, Status: fields, an open/closed split, a "tick items off here" instruction.

## Why this comes to you (the operator)

The skill's wording is planny's product surface; a new rule binds every agent in every project that installs planny.

## Proposal

Add one bullet to the skill's "Rules that keep the store consistent":

"A status-bearing list in a document is a task list. If you are about to write checkboxes, tick marks, Status: fields, or an open/closed item section into a markdown file — whatever it is called: queue, register, backlog, follow-ups, review debt, next steps — stop and planny add each item instead; the document keeps the analysis and cites the task ids."

And one row to the action map: "You're drafting a next-steps / follow-ups / TODO section in a doc → planny add per item, cite the ids in the doc."

*Pros:* catches the failure at the moment of creation (not at session close), names the disguises, and is phrased as an observable tell rather than a category list.
*Cons:* one more rule in an already-long skill.

## Needed from you

"go" (or edit the wording); the skill edit plus an npm release then ships it to every consumer.

## When

No deadline; the claudebox project carries a project-local WORKING.md rule ("Docs record; planny tracks") meanwhile.
