The reviewer's fourth duplicate position computation lives in web/app.js: the board and drawer derive 1-based active positions client-side from the sorted task list, while ops, render and the CLI now share priority.activePosition. The client cannot import that module, so close the gap the other way: /api/state includes each task's active position (from the shared helper), and the board cards and drawer read it instead of computing. One definition everywhere.

Design note (operator asked): no conflict with priority editing. The UI only displays current positions and issues bump commands; every mutation already round-trips through the API and re-fetches state, so server-computed positions arrive with each refresh exactly as the order itself does. The client could not correctly predict a move's landing spot anyway — bumps clamp to the dependency invariant and repairs cascade, so prediction needs the whole priority engine. If drag-and-drop ever arrives, keep it non-optimistic: drop issues the bump command and the refresh shows where the task legally landed.
