The operator asked, 2026-09-02, what happens when the machine cannot work the
host out, and whether the fallback tells the user what to fill in.

The fallback exists and prints the whole command with `<host>` left blank,
but its note only says "fill in <host> yourself". That names the blank
without saying what belongs in it. Someone who has never written an ssh
forward does not know whether it wants a name, an address, a user, or a port.

On the "several connections" worry: there is none. sshd sets SSH_CONNECTION
in the environment of the shell it starts, so each session sees only its own,
and planny reads the one it is running in.

There is a worse case the operator did not name, and it is the dangerous one:
a stale value. A tmux or screen pane carries the environment it was created
with. Reattach from a different machine, or run planny in a pane older than
the current session, and SSH_CONNECTION still names the connection that is
gone. planny would then print a wrong host confidently, which is worse than
printing none, because it looks right.

Done looks like:
- With no session, the note says what belongs in the blank: the name you ssh
  to, or user@address, and where to put -p for a port that is not 22.
- With a session, the note stays but invites checking, so a stale value is
  noticed rather than trusted. It already names the host it used; the wording
  should make clear that is a guess about how the operator reaches this
  machine, not a fact about the machine.
- Both notes stay on stderr, so the command keeps stdout to itself.

Built, 2026-09-02, taking in two steers the operator gave while it was in
progress: hand the facts over so an agent can work it out, and when the guess
fails, say why and say that the failure is normal.

What it prints when it cannot work the host out:

  could not work out how you reach this machine, which is normal and not a
  fault: the address comes from an ssh session, and this command is not
  running in one. A local terminal, a tmux pane older than your session, a
  cron job and a container all look the same from here.
  replace <host> with the name you ssh to, or user@address; put -p <port>
  before the -L flags for a port that is not 22.
  this machine is called mike-box, reachable at 172.20.0.1, 173.26.1.11
  ssh -L 5890:127.0.0.1:5890 … <host>

Four things, in order: what went wrong and that it is expected, what belongs
in the blank, what this machine knows about itself, and the command. Only the
last is on stdout. The machine's name and addresses are there so an agent can
offer candidates to the operator instead of guessing, and so a person can
recognize their own box in the list. The skill now tells an agent to do
exactly that.

When it does work the host out, the note now says "guessing host … from this
shell's ssh session". "Guessing" is the honest word: a tmux pane or a detached
process carries the environment of the session it was made in, which may be
one that has since gone, so the value can name a host that no longer reaches
here. Naming it in the note is what lets the operator catch that.

On the operator's worry about several connections at once: there is none to
fix. sshd sets SSH_CONNECTION in the environment of the shell it starts, so
each session sees only its own, and planny reads the one it runs in.
