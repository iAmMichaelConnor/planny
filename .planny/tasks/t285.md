Reverting t282, on evidence from its first real use, 2026-09-02.

t282 made `--forward` fill the host in from SSH_CONNECTION: the address the
client dialled to reach this machine. The reasoning was that the client can
certainly reach that address, because it just did. That reasoning is wrong
whenever anything sits between the two machines.

What happened. planny printed `mike@173.26.1.11` and the operator trusted it.
That address is not this machine as their laptop sees it: ssh to it asked for
a host fingerprint, meaning it reached something else entirely, while
`ssh mike-box` reached this box and listed all four ports. SSH_CONNECTION
reports what this side of a gateway sees, and a container or a cloud box
almost always has a gateway. So the guess is wrong precisely where planny is
most likely to be used remotely.

Worse than wrong: it was confidently wrong. The operator lost a long stretch
of debugging to a plausible-looking address, and `-N` hides the failure,
because a hanging connect and a working tunnel both print nothing.

Done looks like:
- `--forward` prints `<host>` unless the operator names one. It stops
  answering a question it cannot answer.
- The address from SSH_CONNECTION is still printed, on stderr, as one
  candidate among this machine's own name and addresses, plainly labelled as
  unverified. That is what the operator asked for earlier: give an agent and a
  person the facts to work it out, rather than a guess to trust.
- `--forward <host>` is unchanged, and is now the only way the host gets
  filled in.

Reverted, 2026-09-02. `--forward` no longer guesses. It prints `<host>` unless
the operator names one, and offers what the machine knows as candidates:

  replace <host> with the name you ssh to. These may help:
    this machine calls itself mike-box
    its own addresses are 172.20.0.1, 173.26.1.11
    your session arrived on mike@173.26.1.11
    none of these is necessarily reachable from your machine, and a private
    address may reach a different machine on your own network

The last line is the one that matters. In the case that prompted this, the
guessed address reached a different machine from the operator's laptop — ssh
asked to accept an unknown host key, which is the only reason nothing came of
it. A private address means different machines on different networks, so
printing one as a target is not merely useless off this network, it is
pointing somewhere.

The hostname is listed first, and in this case it was the right answer:
`ssh mike-box` worked. The reasoning in t282 that dismissed hostname as
unreliable was not wrong in general, but it dismissed the one candidate that
happened to be correct while promoting one that was not. Offering all of them
and choosing none is the honest shape.

sshTarget() stays, and is still tested: it now feeds a candidate rather than
an answer. `--forward <host>` is unchanged and is the only thing that fills
the blank.

The skill now tells agents to offer the candidates and ask, never to pick one.
