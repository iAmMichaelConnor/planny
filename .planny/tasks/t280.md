## The decision (t276)

## Background

The shared board (`planny serve --all`, t265) held every plan in one
server and one UI. You asked whether it had overcomplicated the codebase,
then said: "instead, should there just be a thin site that is launched
additionally, which points to the other planny sites at their other
ports", and "perhaps we could have a single command that launches all
plannys on all their independent ports, and the command also launches the
proxy site and gives the user one link? And maybe one command to forward
those ports (when working remotely via ssh)? Idk".

That is built (t272 to t275) on the branch `wanny/boards-index`, in the git
worktree at /mnt/user-data/mike/.worktrees/planny-wanny-boards, because you
asked for no more shared-board commits on main until you were comfortable.
The branch has three commits on top of main:

1. The shared board reverted. src/server.ts, src/cli.ts and web/ are
   byte-identical to the commit before it (b4831e5). The task files under
   .planny/ are untouched. src/discover.ts stays, trimmed to the walk.
2. `planny boards`: finds every plan under your home directory (or each
   `--root`), starts a board for each plan that has none with the same
   detached start every session already uses, and serves one page on port
   5890 that links to them all. `--detach` runs the page detached; `--stop`
   takes the page and every board down; `--forward` prints the `ssh -L`
   flags for the page and every running board, so
   `ssh $(planny boards --forward) <host>` is one paste.

Background terms: a board is the localhost UI for one plan on its own
port; the boards page is the page that lists and links them.

**The numbers.** Against the code before the shared board, the shared
board added 458 lines to src/ and web/ and 424 lines of tests. The boards
design adds 466 lines to src/ (0 to web/) and 356 lines of tests. So the
line count is about the same, and the branch is not smaller code. What
changed is where the lines sit and what they touch:

- The shared board changed the board itself: how every request is routed
  (project-scoped API paths and a key scheme), what a plan's address
  record means (one record written into every plan, a precondition to stop
  fights), a watcher per plan, a picker in the UI, and one process serving
  one UI build for every plan — so editing planny's UI changed every
  board at once, and a rebuild bounced them all.
- The boards design touches none of that. The board, its API and its UI
  are exactly what they were. The new code is one leaf module
  (src/boards.ts, 212 lines, half of it the page's HTML and comments), a
  CLI command with its help text (115 lines), and a small refactor in
  src/server.ts that makes the detached start and the stop one shared
  core instead of copying them. Deleting the feature again would mean
  deleting one module and one command.
- Each board runs whichever planny started it. That settles the dev-mode
  question on its own: a board started from the dev checkout follows edits
  to web/; the others do not.

What is lost against the shared board: switching plans inside one tab.
The page gives one address and one click to any board; each board is its
own tab. Whether that answers "tired of juggling multiple ports": you keep
one address (the page) and never type a port; you do have several tabs.

**Where it runs now.** The live boards were switched over on 2026-09-02:
the page at http://127.0.0.1:5890; planny-wanny's board at :5891 from the
dev checkout (main's dist); claudebox at :5892 and codex-delegation at
:5893 from the branch build in the worktree. Sessions in those plans can
keep running `planny serve --detach` and `planny url` with any planny
build, the global 0.2.2 included: the per-plan record and probe did not
change.

Tests: test/boards.test.ts (8), test/cli.test.ts (3), test/detach.test.ts
(one real-process case: two plans up, the page links them, a second run
changes nothing, `--stop` takes everything down), test/discover.test.ts

## Proposal

Merge the branch into main and run the boards from main:

```
git merge --ff-only wanny/boards-index    # or a plain merge if main moved
npm run build
planny boards --stop && planny boards --detach
git worktree remove /mnt/user-data/mike/.worktrees/planny-wanny-boards
git branch -d wanny/shared-board           # when you no longer want it
```

*Pros:* the board, its API and its UI go back to one plan each, with one
build per board; every piece of multi-plan behaviour is in one deletable
module and one command; the lifecycle of each board is the tested
per-plan one; one command and one link for every board; one line for the
SSH forward.
*Cons:* several tabs instead of one; about the same number of source
lines as the shared board; a walk of your home directory at start (1.3 s
here) and again every 30 s on request.

## Alternative options

- Keep the shared board: leave main as it is and delete the branch. Pros:
  one tab. Cons: the coupling listed above stays, and so does the
  one-build-for-every-board blast radius.
- The page only, without starting or stopping boards: drop `startBoards`
  and `stopBoards` and the start half of the command (about 90 lines
  fewer). Pros: smaller. Cons: no single command; each session starts its
  own board as today, and `--stop` stops only the page.
- Neither: revert to the code before t265 and keep no multi-plan tooling.
  Pros: the smallest codebase. Cons: back to typing ports.
