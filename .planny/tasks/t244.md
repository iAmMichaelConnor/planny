Why: on 2026-09-02 an orchestrator wrote 'planny add … -d "… run `cloxy coverage modules …` …"' in a double-quoted shell string; bash substituted the backticks and ran the command (against a production-pointed CLI; it failed harmlessly that time) and the body lost the quoted text. Done looks like: the skill's 'Creating tasks and plans' section says to use --desc-file (heredoc with a quoted delimiter) or single quotes whenever a body contains backticks, $(…) or other shell-special text, with a one-line example; optionally the CLI warns when a -d body arrives with an empty span where a backtick pair would be (hard to detect — the doc line is the fix).


Built, 2026-09-02, in two places.

The skill's "Creating tasks and plans" section gains a bullet under
Description: a body that quotes a command needs --desc-file, because the
shell runs whatever sits between backticks or inside $(...) in a
double-quoted -d before planny sees it. The command really runs, and the body
keeps an empty space where the text should be. The bullet carries a
three-line example using a quoted heredoc delimiter, and says single quotes
work too but then the body can hold no single quote of its own.

`planny add --help` carries the same warning in four lines. That is where a
reader stands at the moment they need it, and help text cannot drift from the
binary.

The CLI heuristic the task called optional is not built. It cannot be built
honestly: after the shell has substituted, planny receives a body with a gap
in it and no way to tell that gap from prose the author meant. The warning
has to arrive before the command runs, which is what the two doc changes do.
