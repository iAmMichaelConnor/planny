I'm getting tired of juggling multiple ports for different planny sessions. Would it be possible to have a serve all option, which deterministically finds .planny plans on the user's machine (but not ones that exist within worktrees) and host them all? The ui would enable the name of the project (currently in the top-left) to be clickable to select which project the user wants to look at. We'd still completely silo the tasks of each plan (we wouldn't show a combination of tasks from different projects, for example). Each project would basically be viewed the same as we do today, just selectable under a drop-down by clicking the currently-showing project's name in the top-left.


Built, 2026-09-02. `planny serve --all` holds every plan it finds in one
board. The project name in the top-left becomes a picker; choosing another
project shows that plan and only that plan.

**How it finds plans.** A plain walk, not a heuristic, so the answer is the
same every time: from each root, visit every directory down to eight levels
and take any that holds a `.planny`. Roots are the ones given by `--root`
(repeatable), or your home directory when none is given. Three rules keep it
honest and quick:
- A store found is never descended into. A plan inside another plan's tree
  belongs to the outer plan.
- Directories nobody keeps a plan in are passed over: node_modules, .git,
  dist, build, out, target, vendor, .cache, .next, venv, __pycache__, and
  macOS's Library and Applications.
- A `.planny` in a linked git worktree is passed over in favour of the main
  worktree's plan, unless the `fork` marker says that worktree keeps its own
  — the same rule `store.findRoot` already follows for the CLI. That is the
  "not ones that exist within worktrees" the task asked for.

**How the plans stay apart.** Each has a key: its directory name, plus a
slice of the path's hash when two projects share a name. The API grew one
prefix — `/api/projects/<key>/…` — and every route below it is the same
handler the single-plan routes use, so there is one set of routes, not two.
The board fetches, posts and refreshes only inside the project it is showing,
and switching projects clears everything that named tasks of the last one:
the open task, the collapsed rows, the expanded decisions.

**What the operator gets back.** The unprefixed `/api/…` routes still answer
for the first plan, so every existing link and client keeps working, and a
board holding one plan behaves exactly as before, down to the addresses it
uses. `planny url` answers from inside any plan the shared server holds, and
`planny serve --stop` from inside any of them stops it — both because the
server records its address in every plan it serves, and because "is this
port serving my store?" now asks about the whole set instead of the first.

One bug found and fixed on the way: `serve --stop` from a plan that was not
the first would see the first plan's root, decide the record was stale,
delete it and leave the server running. It now checks membership. A
real-process test covers it, because stopping sends a real signal to a real
pid.

**What this does not do**, deliberately: no view mixes two plans, as asked;
there is no cross-project search or queue. The server still binds 127.0.0.1
only, so the trust boundary is unchanged — but note that one server now
reaches every plan it found, which is a wider reach than a single-store
server had.
