The operator's words, 2026-09-02, after the shared board (t265) went live and
they had asked whether it overcomplicated the codebase:

"instead, should there just be a thin site that is launched additionally,
which points to the other planny sites at their other ports. I.e. no shared
planny ui; just a thin proxy which points to the other sites. Yes, that
sounds clean, and sounds like we can roll-back lots of machinery and code
smell."

And then:

"But perhaps we could have a single command that launches all plannys on all
their independent ports, and the command also launches the proxy site and
gives the user one link? And maybe one command to forward those ports (when
working remotely via ssh)? Idk"

## Background terms

- A board: the localhost UI that `planny serve` runs for one plan, on its
  own port.
- The shared board: `planny serve --all`, one server that holds every plan
  (t265).
- The boards page: a small page that lists every plan on this machine and
  links to each plan's own board.

## The design

Each plan keeps its own board on its own port, exactly as before t265. One
new command, `planny boards`, does three things:

1. Finds every plan (the walk from t265 stays, in src/discover.ts), starts a
   board for each plan that has none — the same detached start every
   session already runs (`planny serve --detach`) — and leaves a running
   board alone.
2. Serves the boards page on one fixed address (port 5890, just below the
   range the boards use) and prints that one link.
3. `--stop` takes the page and every board down. `--forward` prints the
   `ssh -L` flags for the page and every live board, so a remote operator
   pastes one line.

## Why this is better than the shared board

The shared board made one process hold N plans. Everything hard followed
from that: project-scoped API routes, a key scheme, a watcher per plan, one
address record written into every plan, the one-plan-one-board precondition
(t268), a picker in the board UI, and one UI build for every plan (editing
planny's own UI changed every board at once, and a rebuild bounced them
all). The boards page keeps one process per plan, so all of that goes. The
lifecycle each board needs — a record, a probe, a detached start, a stop —
already exists per plan and is tested with real processes; `planny boards`
loops over it.

What is lost: switching plans inside one tab. The operator gets one link
(the page) and one click to any board; each board is its own tab.

## Done looks like

The shared board is gone from the code. `planny boards` starts everything
and prints one link; `planny boards --stop` stops everything; `planny boards
--forward` prints the flags. README, CLAUDE.md and the skill say so. The
three live plans are served this way.
