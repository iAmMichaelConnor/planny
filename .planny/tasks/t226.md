## Background

A tracked `.planny` store is committed state, so git operations act on
the plan itself. The worktree redirect (t224) funnels *live* mutation
into one working store, but committed snapshots still diverge across
branches and checkouts, and git reunites them textually. Two git
surfaces hurt:

**Merging branches whose stores diverged** fails in three ways, in
order of certainty:

1. *Id collisions are the common case.* `nextId` is max-plus-one, so
   any two branches that each add one task mint the same id for
   different work. The merge hits an add/add conflict on the same
   `tN.md` with no good resolution — two tasks cannot share one
   filename, and every `parent`/`blocked_by` reference to that id is
   ambiguous.
2. *Same-task divergence.* A task edited on both sides either
   conflicts inside its YAML (history arrays grown on both sides) or —
   worse — merges cleanly hunk by hunk into a combined task neither
   branch ever saw.
3. *Cross-file invariant damage after clean merges.* Each side alone
   is acyclic and consistently ranked; their union can hold dependency
   cycles, duplicate ranks, and blocked-above-blocker orders. A
   textual merge cannot see any of it.

**Checkout and restore** act on the plan too:

- Clean tree, stores differing between branches: `git checkout`
  time-travels the plan wholesale — statuses revert, tasks vanish or
  reappear, the serve UI pushes the old state to the open board live,
  and new work then mints ids from the old maximum.
- Dirty `.planny`, stores differing: git refuses the checkout, so
  constant agent mutation blocks branch switching until plan noise is
  committed or stashed.
- Dirty `.planny`, stores identical at both tips: git carries the
  uncommitted store across silently — the common same-lineage case,
  and the behavior we actually want.
- `git restore .planny` (or `checkout -- .`): the plan of record is
  discarded instantly, with no warning.

Checkouts inside linked worktrees are harmless since t225: the
redirect ignores their copies.

Doctor already covers some aftermath: a conflict-markered file is
flagged unreadable, and duplicate ranks, cycles, dangling references
and order violations are found (ranks and dangling references are
fixable). Missing: merge-specific findings, rewind detection, and any
resolution story for classes 1 and 2.

## Why this comes to you (the operator)

This decides what workflows planny promises to support — one lineage
of truth per project, or plans that branch and merge — and that is a
product boundary, not an implementation detail.

## Proposal (a) — policy, doctor findings, and a rewind tripwire

Document the supported model: one lineage of truth. Commits of
`.planny` are snapshots for history and backup, not merge inputs; the
working store is the plan. Then two small mechanisms:

- Doctor gives a task file containing git conflict markers a specific
  finding ("unresolved merge conflict — resolve the merge, then rerun
  doctor") instead of a generic parse error, and the docs recommend
  running doctor after any merge that touched `.planny`.
- A rewind tripwire: one untracked sidecar, `.planny/last-seen.json`,
  recording the highest id this machine's CLI has minted and the
  newest `updated` stamp it has written — e.g.
  `{"maxId": 226, "updated": "2026-09-01T15:41:00.000Z"}`. Mutations
  advance it under the existing lock, monotonically; every store open,
  reads included, compares and warns on stderr while the store is
  behind ("the store looks older than what this machine last saw — a
  checkout or restore may have rewound the plan"). Reads never write
  it. The alarm repeats until the operator restores the store or
  deletes the sidecar as explicit acknowledgment; a missing sidecar
  means no warning and re-adoption on the next mutation; an unreadable
  one is a fixable doctor finding. This is the `cursors.json` pattern
  exactly — a machine-local sidecar of an existing kind, not a new
  category of state — and it joins `serve.json`, `serve.log` and
  `lock` in t223's planned `.planny/.gitignore`.

*Pros:* small, honest, ships now; catches merge damage and rewinds
loudly (checkout time-travel and `git restore` both trip it) instead
of letting a broken or rewound store limp along.
*Cons:* merging plans across branches remains unsupported; resolving a
collision stays manual.

## Proposal (b) — a git-aware `planny merge`, later

`planny merge` would not run a git merge underneath; it runs inside
one that git has already started. The user merges as usual; git stops
on the store's conflicts, and at that moment the index holds what a
resolver needs: the merge base and both sides of every conflicted path
(the stages `git ls-files -u` lists). `planny merge` reads those,
unions history entries by timestamp, takes field-wise last-writer-wins
by `updated`, and — the crucial part — identifies ids the other side
minted since the merge base, re-mints them onto fresh ids, and
rewrites that side's references to match; then rank repair runs, the
resolved files are staged, and the user commits the merge. (A
per-file gitattributes merge driver cannot do this: re-minting an id
rewrites *other* files' references, and a driver sees one file at a
time.) Semantic duplicates — both branches wrote the same task in
different words — stay a human call, surfaced as warnings.

(b) builds on (a), not instead of it: the policy still names what is
supported, the tripwire still catches rewinds, and (a)'s
conflict-marker finding becomes the signpost that says "run
`planny merge`". Choosing (a) now loses nothing if (b) comes later.

*Pros:* makes cross-branch planning genuinely reliable; keeps the
flat-file store and short sequential ids.
*Cons:* planny grows a git dependency in one command and real merge
machinery with real edge cases; only worth building when divergent
stores are routine (a second machine, a shared repo) rather than an
accident.

## Proposal (c) — untrack the store, decided per repo

Add `.planny/` to the repo's `.gitignore` and `git rm -r --cached` it.
Every hazard above evaporates at the root — no merge conflicts, no
checkout time-travel, no blocked switches, no restore discard, no
cross-branch id minting — and feature-branch diffs stop carrying plan
churn.

What it costs: the repo stops being the plan's backup and time machine
— no whole-board snapshots, no recovering a deleted store from git, no
plan travel to clones or collaborators. Softeners: each task file
already carries its own typed history (statuses, renames, moves, with
stamps and actors), so per-task history survives; `planny export` can stay
the tracked, human-readable snapshot; a later `planny snapshot` could
commit the store to an orphan ref for backup without merge exposure.

Migration caution: `git rm -r --cached` is safe locally, but any other
checkout pulling that commit has its copy deleted by git — go
single-lineage first. Gap to close if adopted: a non-nested linked
worktree of an untracked-store repo finds no `.planny` at all, so
`findRoot` should fall back through the worktree detection when it
finds nothing — the mirror image of the t225 redirect.

The verdict is per-repo: a working repo like claudebox gains the most;
this repo tracks its store partly as dogfood demonstration and can
keep doing so under (a).

## Alternative options

- Merge policy `ours` for `.planny/**` via gitattributes: merges keep
  the target branch's store. Trivial, but silently discards the other
  branch's task updates — a data-loss default.
- Collision-free ids (random suffixes, session prefixes): removes
  failure class 1 at the root, but trades away the short human ids the
  tool leans on, and classes 2-3 remain.
- An append-only operation log as the store of record, state as a fold
  of it: merges become log unions and largely conflict-free. The
  principled fix, and a rewrite of the storage layer; out of scale.
