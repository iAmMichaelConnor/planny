## Background

Agent harnesses tie background tool commands to the session. Claude Code stops them at session end, /clear, and context compaction (anthropics/claude-code issue #25188); on 2026-09-01 this killed a served planny board twice in one overnight session. The recipe that survives is a shell incantation: `setsid nohup planny serve --port <port> >/tmp/planny-serve-<port>.log 2>&1 &`. It works, but an agent can mangle it (quoting, the redirect, shells that differ), and macOS ships no `setsid` binary at all. Tasks t148 (skill) and t149 (README) document the incantation; this decision asks whether the CLI should make it unnecessary.

## Why this comes to you (the operator)

A new CLI surface on your product; its scope and shape are product trade-offs.

## Proposal

Add `planny serve --detach`: the CLI re-launches itself into a new OS session in-process (a detached spawn with stdio to a log file — no `setsid` binary needed, so it also works on macOS), writes the log to a predictable path, prints the URL, log path and pid, and exits 0. Optionally add `planny serve --stop` to end the detached server. The skill and README recipes then collapse to one command an agent cannot get wrong, in every harness and shell.

*Pros:* one command; portable; harness-proof by construction; the t148/t149 wording becomes trivial.
*Cons:* new surface to maintain; a pid file and staleness handling add a little state.

## Alternative options

Docs only — t148 and t149 land the shell recipe and nothing else changes. Zero code, but every agent on every OS repeats a fragile incantation, and macOS agents need a different one.

## Needed from you

"build --detach" or "docs only"?

## When

No deadline; t148 and t149 land either way. An answer before their release lets the skill point at the final recipe once instead of twice.

## Clarification (2026-09-01, operator question)

The operator asked why the detached recipe needs a log file when plain serving needs none. Answer: the server always writes output (the startup URL line, any crash message). Foreground or harness-run, that output lands in the terminal or the harness capture. A detached process has no terminal, so its stdout and stderr must be pointed somewhere: a file, or /dev/null. The redirect to /tmp is not a new need of the server — it is the only place a post-detach failure (port taken, crash hours later) can be read. /dev/null also works, at the price of a board that dies silently with no way to ask why. nohup with no redirect would append to ./nohup.out anyway, so a predictable path beats an accidental one. A built-in --detach faces the same choice, which is why the proposal gives the child a log file too.
