Observed 2026-09-01 in the claudebox store: a session that had read the skill created nine tasks at the root of a store with a curated topical hierarchy (an SP subtree per area, an umbrella per theme), and created an umbrella task duplicating a pre-existing one (t202 duplicated t30, "Fable review pass over the sessions-23-25 core slices"). The skill says "--parent to place it in the hierarchy" as an optional field note, but nothing makes placement a step of adding — and a session adding tasks mid-flow does not naturally stop to read the tree.

Proposal: in "Creating tasks and plans", make placement and duplicate-checking explicit steps of add, phrased cheaply so it does not force reading a whole large tree:

"Before you add: find the task's home and check it is new. A store that has a hierarchy expects new work to join it — look for the parent (planny tree for shape, or planny next --under <area> when you know the area) and pass --parent; a root-level task is a deliberate choice, not a default. And search the open tasks for the same work under other words (planny list --status todo,in-progress piped through grep for the key nouns) before creating an umbrella or theme task — duplicating an existing task forks its history."

Cost of the failure it prevents: floaters make planny next --under incomplete, progress roll-ups wrong, and duplicated umbrellas split one piece of work's history across two ids.
