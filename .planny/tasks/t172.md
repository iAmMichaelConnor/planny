Observed 2026-09-01 in the claudebox store: a session that had read the skill created nine tasks at the root of a store with a curated topical hierarchy (an SP subtree per area, an umbrella per theme), and created an umbrella task duplicating a pre-existing one (t202 duplicated t30, "Fable review pass over the sessions-23-25 core slices"). The skill says "--parent to place it in the hierarchy" as an optional field note, but nothing makes placement a step of adding — and a session adding tasks mid-flow does not naturally stop to read the tree.

Proposal: in "Creating tasks and plans", make placement and duplicate-checking explicit steps of add, phrased cheaply so it does not force reading a whole large tree:

"Before you add: find the task's home and check it is new. A store that has a hierarchy expects new work to join it — look for the parent (planny tree for shape, or planny next --under <area> when you know the area) and pass --parent; a root-level task is a deliberate choice, not a default. And search the open tasks for the same work under other words (planny list --status todo,in-progress piped through grep for the key nouns) before creating an umbrella or theme task — duplicating an existing task forks its history."

Cost of the failure it prevents: floaters make planny next --under incomplete, progress roll-ups wrong, and duplicated umbrellas split one piece of work's history across two ids.

Cost analysis (2026-09-01, operator asked): the search this rule prescribes is name-level only — planny list --status todo,in-progress prints one line per open task, a few hundred tokens even for a large store, and grep trims it further. That is one command per add-moment, far cheaper than the failure it prevents (a duplicated umbrella forks history; merging later costs much more). When this task is worked, the wording must bound the cost explicitly: search names through list, never read bodies wholesale. Related: t173 (open decision) proposes the mechanical layer at add time; see the note there on why the two complement rather than replace each other.

Directive (2026-09-01, operator): the rule must name a cheap command so asking about other tasks never costs real tokens. Design, measured on this store: the text form planny list --status todo,in-progress is already the cheap query — one line per task (status mark, id, name, short suffixes), 512 bytes for this whole active board — and it greps directly. The expensive trap is --json, which carries full bodies; the skill wording must say names come from the text form and forbid --json for this check. Two additions when this task is worked: one, add --compact to list --json (the same shape catchup --compact uses: id, name, status, type, kind, updated) so structured callers get the cheap form under the one flag vocabulary; two, the skill sentence becomes: check for the same work under other words with planny list --status todo,in-progress (one line per task — grep it for the key nouns and their synonyms); never use --json for this. Red first for the flag in test/cli.test.ts.
