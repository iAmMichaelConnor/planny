Enable a user to move the priority of "TODO" status items up and down (click and drag) into a new priority position in the todo kanban column. The user must not be allowed to move an item to a priority that violates its dependencies. There are already codepaths in the cli that ensure priority changes don't violate dependencies of tasks, right? (Aside, hopefully all the buttons for top/bottom/granular priority selection already respect dependencies and don't allow changes to a task's priority that doesn't make sense and would violate the rules?) Also enable it in the tree, although that might be difficult, because of course if moving a nested child, we don't want to allow the child to be moved above its parent (because visually it must be indented). Perhaps, then, it isn't possible to do this for the tree view, but it is for the board view.


Built for the board, 2026-09-02.

Answers to the two questions in the task, both confirmed by reading the code:
yes, every priority change already goes through one funnel — ops.bumpTask,
then bumpPriority — which clamps a move to the nearest position the
dependencies allow. The top, bottom and typed-position buttons all use it, and
so does this drag. Since t246 a clamped move also says so: it returns a
warning naming where the task stopped and which task held it there, and the
board shows that as a toast. So a drag that dependencies forbid does not fail
silently and does not break the rules; it lands at the nearest legal place and
explains itself.

The drag: every card in a ranked column — To do, In progress, Parked — is
draggable. While a card hovers over another, a line marks the side it would
join. The drop posts a bump to the position where it landed, counted from the
order with the dragged card lifted out, which is exactly what bump takes. A
drop back on the starting place posts nothing.

A drop on another column is refused, and the hover shows no line there: that
would be a move and a status change at once, and the status buttons already do
the second. t259 records the cross-column gesture as its own task.

Not built for the tree, as the task expected: a tree row's place is set by its
parent, so a drag there would have to mean either "re-parent" or "reorder
among siblings", and the row's indentation cannot show both. The dependency
nesting mode makes it worse — a row's place there is derived from blockers,
which a drag cannot set. The tree keeps the drawer's parent picker and the
priority buttons.

One thing to watch: the drop raises a confirm dialog, as every other priority
move does (t25, t16). After a drag that reads as heavy. Decision t258 asks
whether those dialogs stay; if they go, this is one of the places that gets
much better.
