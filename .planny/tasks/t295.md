## Background

A task worked by an agent in a git worktree has resume keys: the branch, the worktree path, the agent's session id, commits ahead of the base, whether the tree is clean, and later the merge commit it landed in. Today those live as prose in the task body, by convention (WORKING.md, the parked-body rule). The convention held for t405, t414 and t415 and failed for t261, whose body pointed at notes that no longer exist. planny's frontmatter has no place for such keys: the only advisory field is model; everything else is status, kind, type, parent, priority and history.

The operator asked (2026-09-02): "Perhaps a planny task could have optional fields for worktree, branch, ...? To be filled in when it becomes in progress? I'm not sure if that's clutter or not."

## Why this comes to you (the operator)

planny is your tool and this changes its task schema. It also sets how much of the coding workflow planny should know about.

## Proposal

Add a generic optional key-value map to a task, not named fields. Commands: planny update <id> --set branch=cov/x --set worktree=.claude/worktrees/codex-t405 --set session=01a06311 and --unset <key>. The map is stored under fields: in the frontmatter, printed by show only when non-empty, returned by --json, and shown on the board card for in-progress tasks. No key is required by planny itself; a project may opt in through a store setting such as require_on_start: [branch, worktree] that makes start warn when a listed key is missing, and done warn when landed is unset.

*Pros:* the roster becomes a query (list --status in-progress --json carries branch and worktree); the board shows where each live agent is working; a missing key is a warning at start, which is the moment it is cheap to fix; planny stays generic because the keys are the project's, not planny's.
*Cons:* agents can leave fields stale exactly as they leave prose stale, so the warning at start and at done is what does the work, not the schema; hand-off evidence (gate output, commands) stays prose in the body either way.

Not clutter, on this shape: a task with no fields looks exactly as it does today.

## Alternative options

Named fields (branch, worktree, session). *Pros:* validation and display are simpler. *Cons:* bakes one workflow into a generic tool; every other planny user carries fields they never set.

Keep the prose convention. *Pros:* nothing to build. *Cons:* the roster stays a read of every in-progress body; no warning catches a park without keys until a resume fails.

## Needed from you

Yes or no to the generic fields map; if yes, the implementation is a task in this store. This pairs with claudebox decision t424 (what done means for a subagent): the landed key is where that decision's "Landed in <hash>" line would go.

## When

No deadline. The prose rule in WORKING.md works until fields exist.
