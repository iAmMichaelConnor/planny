A planny command acts on whichever store the current working directory holds. When an agent runs a mutation from the wrong directory, the failure is loud only if the task id does not exist in that other store; when the id exists in both stores, the mutation silently changes the wrong project's task. Near-miss observed 2026-09-01: a cancel meant for the claudebox store ran while cd'd into planny-wanny and failed only because t217 did not exist there.

Proposal: every mutation command (add, update, start, done, todo, cancel, resolve, bump) names the store it acted on in its confirmation line, for example: "added t161 — <name> [store: /mnt/user-data/mike/planny-wanny/.planny]". That makes a wrong-store mutation visible in the output the agent (and its operator) reads, at zero interaction cost.

Optional extras, if cheap: an explicit --store <path> override so scripted callers do not depend on cwd at all; getter commands could also name the store when more than one store has been touched in the process lifetime (probably not applicable — the CLI is one-shot — so the confirmation-line change is the whole ask).

Related: t161 covers the skill-wording side (adding is a mutation; run from the owning project dir). This task is the CLI-side guard.
