## Background

The git-damage work (t226, t228, t236) speaks to the user through
several messages. At store open and scan: the stderr warning "the
store looks older than what this machine last wrote … run `planny
doctor` for what to do". From doctor: `store-rewound` (carrying the
recovery recipe), `merge-conflict`, `unreadable-file`, `id-mismatch`,
`last-seen-unreadable`, `cursors-unreadable`, the dangling-reference
family, `duplicate-rank`, the two cycle findings, `order-violation`,
and `foreign-file` (which also catches mergetool leftovers such as
`t12.md.orig`). From any command: the load refusal for a file whose
frontmatter id disagrees with its filename. Each message carries its
own instruction, but no single page maps symptom to cause to recovery.
The operator asked whether a troubleshooting reference is needed, and
was unsure.

## Why this comes to you (the operator)

More documentation is surface to keep honest; whether the per-message
guidance already suffices is a product-taste call.

## Proposal

Add a short Troubleshooting section to the README, for humans: one
entry per symptom family — the rewind warning, an unresolved merge,
impostor or unreadable task files, garbled sidecar or cursors — each
with the cause and the fix, pointing at `planny doctor` as the
diagnostic throughout.

*Pros:* one place to look before and during an incident; cheap; stays
honest because it points at doctor instead of duplicating it.
*Cons:* some overlap with doctor's own messages; one more section to
maintain.

## Alternative options

- A `references/troubleshooting.md` inside the skill, for agents.
  Ruled out for now: agents meet doctor's messages at exactly the
  moment they need them, and the stop rule in the skill covers the
  rewind case.
- Do nothing: every message is already a recipe. Viable — the README
  section mostly adds discoverability before anything goes wrong.

## Needed from you

"add the README section", "skill reference too", or "leave it".

No deadline; nothing blocks on this.
