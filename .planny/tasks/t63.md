withLock sleeps with Atomics.wait, which blocks the event loop; under lock contention the serve process stalls every request for up to the 2s timeout. Fine for a single-operator localhost board — the reviewer flagged it as worth knowing, not broken. If planny ever serves more than one person or long-held locks appear: add an async withLockAsync for server routes (setTimeout-based retry), keeping the sync path for the CLI.

Scope clarified (operator asked): concurrent agents on the CLI are the designed, safe case — separate processes contend on the lock file, each blocks only itself, ops hold the lock for milliseconds, and the 2s timeout ends in a retryable error, never corruption. Multiple UI tabs are also safe: one serve process serializes their requests naturally. The only affected path is the serve process itself waiting on a lock held by an external (agent) process — during that sync wait it serves nothing, reads and the event stream included, for up to 2s worst case. Rare, brief, bounded; hence low priority. The async fix targets only the server's routes.
