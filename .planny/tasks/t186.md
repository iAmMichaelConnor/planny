Operator-directed redesign, 2026-09-01: a resolution must not be losable. Resolving a decision creates an outcome task; rejecting closes the decision without one.

## Behavior

planny resolve (and both UI funnels) on a decision, unless rejecting:
1. Appends the outcome to the decision as today (## Outcome, resolvedAt, history).
2. Creates an outcome task in the same locked mutation: kind ai, parent = the decision (the link is the existing canonical parent field — no new schema, children are derived, show/tree/drawer all display it for free). Name: "Act on the outcome of tNN: <decision name>". Body leads with boilerplate: this task records the outcome of decision tNN; the operator has decided; create tasks from this one where the outcome needs work, check the tasks the resolution already unblocked (listed programmatically) before creating duplicates, then mark this task done. Then the full decision text for background, then the outcome.
3. Appends "Outcome task: tNN" to the decision body programmatically — the citation cannot be forgotten because ops writes it.

Reject: a new button in the tiles and the drawer, and planny resolve --reject. Confirm popup first: the decision closes as decided-no and no task is created. The outcome section reads "Rejected — closed without action." (typed text becomes the rejection reason). The existing cancel stays for questions that never needed answering.

## Design choices it touches (the audit the operator asked for)

- "Interpret the response immediately" (skill): softens — interpretation now has a durable carrier; the in-loop agent works the outcome task instead of acting from chat memory. Catchup keeps its role (cross-session awareness) — not violated, complemented.
- One canonical side per relationship: honored — parent, not a new outcome_task field; prose citation is a convenience on top.
- Ops-only mutation + one lock: honored — the resolve and the create are one mutation.
- Double representation risk: a decision that blocks tX yields both an unblocked tX and an outcome task. The boilerplate names the unblocked ids so the picker-upper reconciles instead of duplicating.
- No-work outcomes (wait-for-a-trigger answers) still spawn a task; closing it as done is the recorded confirmation that nothing was needed.
- Priority: the outcome task joins at the bottom like any add. Inheriting the decision's rank would collide with the unique-rank expectation doctor checks; not worth it.
