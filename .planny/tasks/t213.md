## Background

Outcome tasks (built in t186) are plain tasks: kind ai, child of their decision, named "Act on the outcome of tNN", cited by the decision's ops-written "Outcome task: tNN" line. The operator asks whether they have earned a third task type beside task and decision.

## Why this comes to you (the operator)

`type` lives in the ratified store format (t1) — a compatibility surface. Old binaries reject unknown types when parsing, so a third type is the most expensive change the format can take and needs a migration story.

## Proposal

Not yet. The distinguishing property is fully derivable — parent is a resolved decision that cites this id — so every wanted affordance (a UI badge, a filter, a cancel warning, a doctor check) can key on a derived flag at zero format cost. When a consumer wants it, serve `isOutcome` the way `blocked` is served: derived at the API, never stored. Revisit only when ops must behave differently for outcome tasks in a way a derived check cannot express.

*Pros:* zero format risk; no special-casing — outcome tasks keep working as plain tasks everywhere; matches the derive-don't-store design.
*Cons:* the derived check parses an ops-written body line rather than reading a field; a future behavior difference would reopen this.

## Alternative options

- Add `type: outcome` now. Structural identification and native filtering; but every old reader hard-rejects the store, so it costs format versioning and a migration, spent on something derivable.
- Do nothing at all, ever. Cheapest; but if a consumer wants outcome affordances, each will invent its own detection.

## Needed from you

"not yet, derive when wanted" (the proposal), "add the type now", or "never".

## When

No cost to waiting. The answer matters before anyone builds outcome-specific affordances.

## Clarification (2026-09-01, operator question)

The operator notes the code already understands outcome tasks — correct, and the proposal's framing was too strong. Inventory: ops creates them (name, boilerplate, parent, rewiring, citation); query parses the citation for lookups (t210); catchup, resolve --json, the server response, both text renderers and the UI's green note all carry or name outcomeTask; the skill documents the workflow. What does not exist: any classification from the task's own side — no mutation branches on whether a task is an outcome task, and the task object carries no marker. The knowledge flows one way, from the resolve event and the decision's citation. The question this decision really asks: when a consumer needs the reverse lookup (a card badge, a cancel guard asking 'am I an outcome task?'), should that be a stored type on the task, or a derived check through the parent link and citation? The proposal stands: derive it, until ops itself needs a behavior no derived check can express.
