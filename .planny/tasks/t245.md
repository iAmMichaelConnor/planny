Observed 2026-09-02 in the claudebox store: the orchestrator ran 'planny resolve t295 --response …' and, within the same minute, the agent that had created t295 ran its own resolve; planny created two outcome tasks (t296 and t297) with identical names 'Act on the outcome of t295: …'. Done looks like: a second resolve on a decision whose status is already resolved is refused with a message naming the existing outcome task (or, with --force, appends the new response to the existing outcome instead of creating another); 'planny doctor' flags duplicate outcome tasks for one decision. Repro: resolve the same decision twice from two shells.


Built, 2026-09-02. ops.resolveDecision now refuses a second resolve on a
decision that already carries a resolved stamp. The message names the outcome
task that already holds the answer (or says the decision was rejected, so
nothing was created), and it says how to get back in: `planny todo <id>`
reopens the decision, which clears the stamp, and the answer can then be
recorded again. The refusal writes nothing — no second outcome section, no
second task.

One deviation from the plan above, with the reason: there is no --force flag.
Reopening already does exactly what --force would do, through a command that
exists and reads honestly ("I am reopening this question"), and it clears the
resolved stamp so the store never claims two answers at once. A second way in
would be a second codepath for one act.

planny doctor gains 'duplicate-outcome' (warning, not fixable): a decision
whose body cites more than one outcome task that is still open. Not fixable
because choosing which answer survives is a judgement call. Outcome tasks
already finished do not count, so a deliberate reopen-and-answer-again leaves
no finding.
