Found on the first real `serve --all`, 2026-09-02. Another session already had
its own board up for one of the plans (claudebox, on 5892). Two things went
wrong.

**It refused to start.** `serve --all --detach` printed "already serving this
store at http://127.0.0.1:5892" and did nothing. The check asks "is the first
plan already served?", but a server holding one of the plans is not the
server we asked for. It should count as already running only when it holds
every plan we mean to serve.

**It would have hijacked the other board's address.** A server records its
address in every plan it holds, so a shared server starting up would
overwrite the serve.json of a plan that already has its own board. That
plan's `planny url` would then point at the shared server instead of the
board its own session started, and `serve --stop` there would stop the wrong
one.

Done looks like:
- "already serving" means a live server that holds every plan this command
  means to serve; anything less is a different server, and we start ours.
- Starting leaves alone the address record of any plan a different live
  server already holds, and says which plans it skipped, so an existing
  board keeps its address.
- Stopping removes only the records this server wrote.

Files: src/server.ts, src/cli.ts, test/server.test.ts.


Fixed, 2026-09-02 — and the first fix was thrown away, which is the part
worth recording.

**The wrong fix.** I started letting a shared board and a per-plan board hold
the same plan at once: the shared one would claim only the address records
nobody else held, and clear only what it claimed. That is fifteen lines of
new bookkeeping, a new `claimed` field on the running server, and a new
question nobody had to answer before — who owns this plan's address? The
operator asked whether the shared board had overcomplicated the codebase, and
for that piece the answer was yes. It is backed out.

**The right fix.** Restore the invariant that `--all` broke: one plan, one
board. Before serving, `serve --all` asks each plan it found whether it
already has a live board. All of them means this command is already running,
which is a success no-op. Some of them means a different server holds those
plans, and it refuses, naming each plan and its address and saying to stop it
with `planny serve --stop` in its directory. None of them starts normally.

That is one check in the CLI, where preconditions belong. The server keeps
the behaviour it always had: it records its address in every plan it serves,
and clears every one on the way out, because it is the only board those plans
have.

The second bug in this task fell out of the same rule: "already serving" no
longer means "the first plan is served by something", so a per-plan board no
longer blocks `--all` — `--all` either takes over from nothing, or says
plainly what is in its way.
