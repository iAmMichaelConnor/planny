## Background

planny stores each task as one markdown file with YAML frontmatter, in one
flat directory: `.planny/tasks/<id>.md`. Hierarchy and dependencies are
frontmatter fields (`parent`, `blocked_by`); the inverse sides (children,
"blocks") are derived, so the two sides can never disagree. Priority is a
sparse integer rank kept consistent with dependencies. The founding prompt
suggested a nested file tree of markdown files, with child tasks in child
directories, and asked for a view on it — this is the answer, built the
other way. It is built, covered by 143 tests, and runs in this repo (this
task list lives in it). The store is meant to be committed to git.

## Why this comes to you (the operator)

The store format is the compatibility surface of the tool. Once other
projects hold `.planny` directories, a format change needs a migration
script. You proposed the nested-tree layout, so the departure needs your
sign-off. If the answer is no, we write a migration to the layout you pick
and re-derive the affected code paths (store, exports, skill).

## Proposal

Keep the flat markdown store.

*Pros:* ids and file paths stay stable when a task is re-parented (a rename
of `parent:` — no file moves), which keeps references from chat logs, commits
and other tasks valid; files stay greppable and hand-readable; one task per
file keeps git diffs and merge conflicts small.
*Cons:* the hierarchy is not visible in a plain file browser — you need
`planny tree`, the export, or the UI; a very large project puts many files
in one directory.

## Alternative options

- Nested directories per parent. Navigable in a file browser, but every
  re-parent moves files, which breaks recorded paths and churns git history.
- JSON files. The structured fields fit, but long markdown bodies become
  escaped strings nobody can read or diff.
- SQLite. Real queries, but opaque to grep and git, and it needs schema
  migrations from day one. AI agents read files better than databases.

## Needed from you

"keep", or name the layout to migrate to.

## When

Before another project adopts the store. After that, a change costs a
migration script and a coordinated upgrade.
