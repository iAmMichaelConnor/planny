## Background

planny finds its store by walking up from the current directory to the
nearest `.planny`. A git worktree checks out every tracked file, and a
repo that tracks `.planny` (this one does; so does claudebox) therefore
gives every worktree a full copy of the store, frozen at the branch
point. Observed live on this machine, 2026-09-01: claudebox's main
store holds 236 task files while its two worktree copies hold 227
each, and three planny servers on three ports each show a different
truth of the same plan. Subagents in worktrees mutate their fork while
the main plan moves on.

Merging the branch back is a plain git text merge of task files —
hand-editing by another name. Disjoint edits may survive; these do
not: both sides mint the same next id for different tasks (an add/add
conflict on the same tN.md, breaking the ids-never-reused invariant),
`.planny/cursors.json` merges into nonsense, and a task whose history
grew on both sides conflicts line by line. doctor can repair dangling
references and duplicate ranks after such a merge; it cannot
un-collide ids.

## Why this comes to you (the operator)

Whether a worktree is the same plan or a deliberate fork is a product
call, and it decides what the board shows you.

## Proposal

Make store discovery worktree-aware. When the `.planny` that discovery
found sits inside a linked git worktree (cheap to detect with no git
dependency: a linked worktree's `.git` is a file that starts
`gitdir:`), and the main worktree holds a `.planny` at the same
relative path, use the main worktree's store and say so once on
stderr. A marker file (for example `.planny/fork`) opts a worktree
into keeping its own store deliberately. Every planny command in a
worktree then reads and writes the one plan through the existing lock;
`serve` and `url` resolve to one board on one port; subagents need no
configuration.

*Pros:* fixes the observed split with no per-repo setup; the lock
already handles concurrent writers; one board, one port, one truth.
*Cons:* implicit behavior — a user who wants an isolated plan must
learn the marker; discovery gains a git-layout case to test (nested
and non-nested worktrees, a main worktree with no store).

## Alternative options

- Stop tracking `.planny` in git. A worktree then has no copy, and
  walk-up discovery reaches the main repo's store when worktrees nest
  inside it (claudebox's layout). Ruled out for now: it forfeits the
  plan's git history, non-nested worktrees still need a pointer, and
  moving existing repos off a tracked store is churn.
- A pointer-file redirect: `.planny` as a file naming the real store,
  like git's own `gitdir:` file. Explicit, no magic — but a tracked
  `.planny` directory reappears in every checkout, so a pointer can
  only pair with untracking.
- Leave it and document "do not run planny inside a worktree".
  Cheapest; relies on every agent reading the warning, and the
  three-board split shows how that goes.

## Needed from you

"make discovery worktree-aware" (recommended), one of the
alternatives, or "leave it".

## When

Before the next multi-worktree claudebox session; every one forks the
plan further and mints collision-bound ids.

Operator's framing, 2026-09-01: a planny executed within a worktree could check where it runs from while walking up, and on seeing a linked worktree use the main worktree's existing .planny instead of its own. Confirmed as the proposal, with two refinements the build must include: (1) the redirect applies even when the worktree already contains a checked-out .planny fork — preventing init is not enough, because tracked stores materialize in every checkout; (2) planny init inside a linked worktree should refuse (or point at the main store) unless the fork marker is given. Implementation edges: gitdir: paths in the .git file can be relative (resolve against the worktree); derive the main root via the commondir file rather than string-stripping; a bare or storeless main worktree falls back to the local .planny with a warning.
