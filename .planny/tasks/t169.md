## Background

The CLI acts on whichever store owns the current working directory. On 2026-09-01 a cancel meant for the claudebox store ran while cd'd into planny-wanny; it failed only because the id did not exist there. t161 fixes the skill wording, t162 makes every mutation confirmation name the store it acted on (visibility after the fact). The operator asks: should every command take the project name and reject on mismatch — or is that cumbersome?

## Why this comes to you (the operator)

The shape of every CLI invocation is your product surface.

## Proposal

Optional assertion, not a mandatory argument. Add `--project <name>` (global flag) and the environment variable `PLANNY_PROJECT`: when either is present, the CLI compares it to the discovered store root's basename and refuses the command on mismatch, naming both. When absent, behavior is unchanged. The skill then tells agents to export PLANNY_PROJECT once per project, exactly like PLANNY_SESSION — so agents (the ones observed misfiring) always carry the guard, and humans typing commands pay nothing.

*Pros:* zero friction when unused; agents get a hard guard by default via the skill; the env form survives cd mistakes inside one session; composes with t162's visible confirmations.
*Cons:* two config surfaces to document; a wrong exported name blocks correct commands until cleared.

## Alternative options

- Mandatory project argument on every command. Strongest guard, but every human invocation pays it, every existing script breaks, and an agent that can paste the wrong cwd can paste the wrong name too.
- Confirmation lines only (t162 alone). No new input surface, but the mistake is caught after the write, not before.

## Needed from you

"optional assertion" (the proposal), "mandatory", or "t162 alone".

## When

Before t162 is built is convenient (same code area), not required.
