The operator asked, 2026-09-02, whether the machine serving the boards can
work out how the user reaches it, so `--forward` prints a line that needs no
editing at all.

It usually can. Inside an ssh session the shell carries SSH_CONNECTION:

  SSH_CONNECTION=173.26.0.1 60664 173.26.1.11 22

The third field is the address the client connected to, and the fourth is the
port it used. With $USER that gives a target the client is known to be able
to reach, because it just did: mike@173.26.1.11, port 22.

What it cannot know is the name the user types. An alias in their own
~/.ssh/config lives on their machine alone. The address still works, so the
line is pasteable either way; it just may not look like what they usually
type.

Done looks like:
- `--forward [host]` takes an optional host, and an explicit one always wins.
- With none, the target comes from SSH_CONNECTION as <user>@<server address>,
  with `-p <port>` when the port is not 22.
- With neither, it stays `<host>`, as now.
- The command goes to stdout alone, so `$(...)`, a pipe or a paste all work.
  Where the guess came from goes to stderr, where it cannot pollute them.

Notes for whoever builds it: hostname() is not good enough on its own —
here it happens to be mike-box, but on a cloud box it is usually something
like ip-10-0-0-5, which means nothing to the client. And a session reached
through a jump host may report an address the client cannot dial directly,
which is why an explicit host must always win.

Built, 2026-09-02. `--forward` now fills the host in itself, so in the common
case the line needs no editing at all:

  $ planny serve --all --forward
  host mike@173.26.1.11 read from this ssh session; pass one to --forward to override
  ssh -L 5890:127.0.0.1:5890 -L 5892:… -L 5893:… -L 5891:… mike@173.26.1.11

The note goes to stderr and the command to stdout, so the command survives a
pipe, a `$(...)` and a paste untouched.

Where the host comes from, in order: the one named on the command line
(`--forward my-box`) always wins; then the address the operator's own machine
dialled to reach this one, read from SSH_CONNECTION, with the session's user
in front and `-p <port>` when the port is not 22; then `<host>` as before.

Two things it will not do, and why. It never uses this machine's hostname:
here that happens to be mike-box, but on a cloud box it is usually something
like ip-10-0-0-5, which means nothing to the client. And it cannot know the
alias in the operator's own ssh config, which lives on their machine alone —
the address still connects, it just may not look like what they usually type,
which is what the named host is for. A session reached through a jump host
may also report an address the client cannot dial directly; the same override
covers it.
