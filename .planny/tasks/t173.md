## Background

Two agents writing to one store can add the same work under different words. Observed 2026-09-01 in the claudebox store: an agent created "Fable-review the Opus-only window of 2026-08-28/29" while "Fable review pass over the sessions-23-25 core slices" sat open — the same work, and the duplicate was found only by a later manual read of the tree. The moment of `planny add` is the one cheap point where a duplicate can be caught before the two tasks fork history. The skill already tells agents to read the plan before adding; wording alone did not prevent this case.

## Why this comes to you (the operator)

This adds behavior to every `planny add` in every store. Whether the protection is worth the noise is a product-taste call, and the review session that proposed it flagged it as speculative.

## Proposal

`planny add` compares the new task's name (plain token overlap — no embeddings, no network) against open tasks. When a likely match exists, the confirmation line gains a non-blocking warning: `added t202 — … (similar open task: t30 "Fable review pass …" — planny cancel --replaced-by if one supersedes the other)`. Never a prompt — multi-writer agents must not hit interactive questions. `--no-similar-check` opts a bulk migration out.

*Pros:* catches duplicates at the only cheap moment; costs one linear scan per add; nothing changes when no match is found.
*Cons:* token overlap is crude — a store whose names share stems ("Release 0.1.x: …", "Skill: …") will warn falsely, and repeated false warnings teach readers to skim past the warnings funnel, which also carries the blocked and active-children warnings that matter; a threshold needs tuning and invites fiddling; an agent may over-trust the hint and cancel a non-duplicate.

## Alternative options

- Doctor-side instead: `planny doctor` reports likely-duplicate pairs on demand. No per-add noise, works retroactively over the whole store; but it catches duplicates late, after both tasks have history.
- Skill-side only: sharpen the read-the-plan-before-adding rule. Zero code; relies on the discipline that already failed once.
- Do not build: accept the occasional duplicate, fix with `planny cancel --replaced-by` when noticed.

## Needed from you

"build at add time" (the proposal), "doctor instead", "skill only", or "don't build".

## When

No deadline. Each duplicate that lands meanwhile costs one cancel-with-replacement to repair.
